# Monitoring and alerts

## Stack

| Concern                | Tool                                                                      | Where configured                                     |
| ---------------------- | ------------------------------------------------------------------------- | ---------------------------------------------------- |
| Errors + performance   | **Sentry**, one project each: `hp-api`, `hp-worker`, `hp-web`, `hp-admin` | `SENTRY_DSN` per service (Render env group / Vercel) |
| Scheduled-job liveness | **Sentry Crons** check-ins from the worker                                | App code (see "App changes required")                |
| Uptime + heartbeats    | **Better Stack Uptime** (30 s checks, 3 regions)                          | Better Stack dashboard                               |
| Logs                   | Render logs → **Better Stack Logs** via Render log stream (pino JSON)     | Render → Workspace → Log Streams                     |
| Host metrics           | **Render metrics** (CPU, memory, instance restarts, HTTP 5xx, latency)    | Render dashboard → service → Metrics / Notifications |
| Payments               | **Stripe** webhook failure emails + Dashboard → Webhooks                  | Stripe → Settings → Team & notifications             |
| Edge                   | **Cloudflare** analytics, WAF/rate-limit events                           | Cloudflare → Security → Events                       |

Health endpoint: `GET /api/v1/health` returns 200 `{db:"ok",redis:"ok"}` or 503. It checks dependencies, so today it is a **readiness** check. Render's `healthCheckPath` uses it (see `render.yaml`); once a dependency-free `/api/v1/health/live` exists, point Render at that so a Postgres blip doesn't make Render cycle every instance, and keep uptime monitoring on `/api/v1/health`.

## Paging

- **Page** (phone + push, 24/7): SEV1 alerts → primary on-call, escalate to secondary after 15 min unacknowledged.
- **Notify** (Slack `#hp-alerts`, business hours): SEV2/SEV3.
- Open hours for business alerts: 08:00–22:00 store time (`America/Los_Angeles`, adjust when the business confirms).
- Contacts: [on-call.md](on-call.md).

## App changes required (backend/frontend owners)

1. **Sentry SDK**: `@sentry/node` in `apps/api` (`server.ts` and `worker.ts`, initialised before other imports, `environment` = `NODE_ENV`/deploy env, `release` = Render `RENDER_GIT_COMMIT`), Express error handler integration placed before `createErrorHandler`; `@sentry/nextjs` in `apps/web` and `apps/admin`. Scrub: no request bodies, cookies or `authorization`; `sendDefaultPii: false`. Add `SENTRY_DSN` (optional) to `apps/api/src/config/env.ts`. Tag webhook/payment errors with `area: payment`.
2. **Liveness route**: `GET /api/v1/health/live` → 200 with no dependency checks (keep `/api/v1/health` as readiness).
3. **Worker cron check-ins**: wrap the two maintenance jobs with `Sentry.withMonitor("release-expired-reservations", …, { schedule: { type: "interval", value: 1, unit: "minute" }, checkinMargin: 3, maxRuntime: 2 })` and `purge-expired-carts` (hourly).
4. **Ops-metrics job** (worker, every 5 min) emitting one structured log line `{"msg":"ops.metrics", paidOrdersLast3h, pendingPaymentOverdue, emailWaiting, emailDelayed, emailFailed, maintenanceFailed, oldestEmailWaitingSec, webhookErrors15m}` — Better Stack Logs alerts on those fields (B1, B3, B6, B7). Counts come from Prisma (`Order` by `paidAt`/`status`/`reservationExpiresAt`) and BullMQ `Queue.getJobCounts()`.
5. **Webhook outcome log**: log `{"msg":"stripe.webhook", outcome: "ok"|"duplicate"|"bad_signature"|"error", type}` per request (no payload) so B2 can be computed from logs.

## SQL checks (run read-only against a replica or with care in prod)

```sql
-- B1: paid orders in the last 3 hours
SELECT count(*) FROM "Order" WHERE "paidAt" > now() - interval '3 hours';
-- B3: pending payments past their reservation
SELECT count(*) FROM "Order"
WHERE status = 'PENDING_PAYMENT' AND "reservationExpiresAt" < now() - interval '5 minutes';
```
